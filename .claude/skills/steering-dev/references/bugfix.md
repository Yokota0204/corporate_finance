# 手順1：バグ調査（バグ修正）

目的は、**根本原因**を特定して design.md の「バグの調査結果」を書ける状態にすること。症状を消すだけの修正は、別の形で再発しやすい。

この段階ではコードを修正しない。調査用に一時的にログを足すなどした場合は、調査後に元に戻す。

## 進め方

1. **症状を整理する。** 期待する動き・実際の動き・再現手順・発生条件（環境、データ、頻度）。報告から分からなければユーザーに聞く。エラーメッセージやログがあれば全文をもらう。
2. **再現する。** 可能ならテストやスクリプトで再現させる。再現できたコードは、そのまま test_case.md の「バグを再現するテスト」の土台になる。再現できない場合は、その旨と、どこまで試したかを報告する。
3. **原因を特定する。** 症状が出ている場所からデータの流れをさかのぼり、最初に値や状態がおかしくなる箇所を探す。関係しそうな直近の変更があれば `git log` / `git blame` も確認する。仮説を立てたら、コードやテストで確かめる。推測のまま原因として書かない。
4. **影響範囲を調べる。** 同じ原因・同じパターンのコードが他にないか、修正で挙動が変わる呼び出し元がないか。
5. **ユーザーに調査結果を報告する。** 次の形で簡潔に伝え、この内容で design.md を書くことの了承を得る。

```
■ 症状: …
■ 再現手順: …
■ 根本原因: `src/xxx.js:42` で … のため …
■ 根拠: （確かめた方法）
■ 影響範囲: …
■ 修正方針案: …
```

## 注意

- 調査の途中で別のバグが見つかったら、今回の対象に含めるかをユーザーに確認する。
- 「期待する動き」が仕様として決まっていない場合（バグなのか仕様なのか判断できない場合）は、ユーザーに確認する。仕様変更として進めるべきなら、モードを切り替えることを提案する。
