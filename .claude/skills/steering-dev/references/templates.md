# ステアリングファイルのテンプレート

※ は必須項目。該当しない任意項目は、見出しごと削除するか「なし」と書く。
テンプレートの `<...>` は置き換える。例示の内容はそのまま使わない。

## 目次

1. requirements.md
2. design.md
3. test_case.md
4. tasklist.md

---

## 1. requirements.md

```markdown
# 要求: <開発タイトル（日本語）>

- 種別: 機能追加 / 仕様変更 / バグ修正
- 作成日: YYYY-MM-DD

## 変更・追加する機能の説明（※）

<何を、なぜ変えるのか。仕様変更なら「現状 → 変更後」。バグ修正なら「期待する動き」と「実際の動き」。>

## 受け入れ条件（※）

- [ ] <第三者が検証できる形で書く。「〜のとき、〜となる」>
- [ ] <異常系・境界値の条件も含める>

## 制約事項

- <使う・使わない技術、互換性、性能、スコープ外とすること など>
```

書き方の注意：受け入れ条件は、後で test_case.md と動作確認チェックリストに落とし込める粒度にする。「使いやすくする」のような検証できない表現は避ける。

---

## 2. design.md

````markdown
# 設計: <開発タイトル>

## バグの調査結果（※ バグ修正のみ）

- 症状:
- 再現手順:
- 根本原因: <ファイル:行 と、なぜ誤動作するか>
- 根拠: <どう確かめたか>

## 実装アプローチ（※）

<方針を2〜3行で説明したうえで、変更内容をコードで書く。>

### `<path/to/file.ext>`

```diff
- 変更前のコード
+ 変更後のコード
```

<新規ファイルならコード全体、または主要な関数のシグネチャと中身の骨子。>

## 変更するコンポーネント（※）

| ファイル / コンポーネント | 変更種別 | 概要 |
|---|---|---|
| `src/...` | 修正 / 新規 / 削除 | ... |

## 影響範囲の分析（※）

- <変更箇所を呼び出している箇所と、そこへの影響>
- <既存データ・既存テスト・他機能への影響>
- <影響がないと判断した範囲と、その理由>

## データ構造の変更

<スキーマ、型、API のリクエスト/レスポンス、保存形式などの変更。変更前後を並べる。なければ「なし」。>
````

書き方の注意：
- 実装アプローチは**コードベースで**書く。文章だけの設計は解釈のずれが出やすい。差分（diff）形式か、変更後のコードを載せる。
- コードは実際のファイルを読んだうえで書く。存在しない関数や変数を前提にしない。

## 3. test_case.md

```markdown
# テストケース: <開発タイトル>

- テストフレームワーク: <例: Vitest / pytest / node:test>
- テストファイル: <配置するパス>

## 単体テスト

| ID | 対象 | 前提・入力 | 期待結果 | 対応する受け入れ条件 |
|---|---|---|---|---|
| U-01 | `func()` | ... | ... | 条件1 |
| U-02 | `func()` | 空の配列 | 空の配列を返す | 条件2 |

## 結合テスト

| ID | シナリオ | 手順 | 期待結果 |
|---|---|---|---|
| I-01 | ... | 1. ... 2. ... | ... |
```

書き方の注意：
- 表の方が分かりやすい場合は表を使う。パターンの組み合わせが多いときは、条件を列にしたテストケース表（デシジョンテーブル）にする。
- 正常系だけでなく、境界値と異常系を含める。
- バグ修正では、**修正前は失敗し、修正後に成功する再現テスト**を必ず1つ以上入れ、そのことを明記する。
- 各ケースに ID を振る。tasklist.md から ID で参照する。
- 自動テストにしにくいもの（見た目、実機依存など）は、ここではなく tasklist.md の動作確認チェックリストに回す。

## 4. tasklist.md

```markdown
# タスクリスト: <開発タイトル>

## 実装タスク（※）

- [ ] 1. <タスク名>
  - 対象: `src/...`
  - テスト: U-01, U-02 を先に書き、失敗を確認してから実装
- [ ] 2. <タスク名>
  - 対象: ...
  - テスト: I-01

## 完了条件

- [ ] test_case.md のテストがすべて成功する
- [ ] 既存のテストがすべて成功する
- [ ] requirements.md の受け入れ条件をすべて満たす

## レビュー工程

- [ ] リファクタリング確認（simplify）: <対応した指摘 / 見送った指摘>
- [ ] セキュリティ確認（security-review）: <対応した指摘 / 見送った指摘>
- [ ] ユーザーによる実環境テスト

## 動作確認チェックリスト（※）

### <機能・修正 1 の名前>

- [ ] **準備**: <用意するデータ。例: 完了済みタスク2件、未完了タスク1件を登録しておく>
      **操作**: <条件・操作。例: 一覧画面で「完了」フィルタを選ぶ>
      **期待**: <どうなるか。例: 完了済みの2件だけが表示され、未完了の1件は表示されない>
- [ ] **準備**: ...
      **操作**: ...
      **期待**: ...

### <機能・修正 2 の名前>

- [ ] ...
```

書き方の注意：
- すべての項目をチェックボックス（`- [ ]`）で書く。作業が進むたびに `- [x]` に更新する。
- 実装タスクは、1タスクで1つのテストサイクル（テストを書く → 失敗 → 実装 → 成功）が回る大きさにする。
- 途中で追加したタスクには「（追加: 理由）」と書き添え、元からあったタスクと区別できるようにする。
- 動作確認チェックリストは、実装・修正した**機能ごとに**、ファイルの最後に書く。「どんなデータを用意し、どんな条件（操作）で、どうなるか」が分かる粒度にする。「正しく動くこと」のような書き方はしない。
