# 手順1：ヒアリング（機能追加・仕様変更）

目的は、requirements.md の「機能の説明」と「受け入れ条件」を書ける状態になること。そこまで分かったらヒアリングは終える。聞きすぎると依頼者の負担になる。

## 進め方

1. **先にコードベースを読む。** 関連する画面・API・モデル・既存テストを確認し、コードを読めば分かることはユーザーに聞かない。
2. **分からない点だけを、まとめて聞く。** 1回に3〜6問程度に絞る。1問ずつ往復すると時間がかかる。選択肢を示せる質問は「A / B / その他」の形にし、おすすめがあれば理由を添える。
3. 回答を受けて、まだ曖昧な点があれば追加で聞く。依頼が十分に具体的なら、ヒアリングは短い確認だけでよい（「〜という理解で requirements.md を書きます」）。

## 観点（該当するものだけ）

- **目的**：なぜその機能が必要か、誰が使うか。目的が分かると、仕様の細部を判断しやすくなる
- **振る舞い**：入力・出力・画面上の動き。正常系の具体例を1つもらえると早い
- **境界と異常系**：空・上限・不正な値・権限がないとき・同時操作
- **既存機能との関係**：既存の挙動を変えてよいか、既存データの移行が必要か（仕様変更では特に重要）
- **スコープ外**：今回はやらないこと
- **非機能**：性能、対応ブラウザ・環境、アクセシビリティなど、気にしているものがあれば
- **技術的な指定**：言語・ライブラリ・テストフレームワークの指定があるか。既存のテストの仕組みがなければ、何を使うか

## 仕様変更のとき

「今どう動いているか」をコードから読み取り、「現状 → 変更後」の形でユーザーに確認する。現状の理解がずれていると、変更の設計が丸ごとずれる。
