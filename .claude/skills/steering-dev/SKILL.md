# ステアリング駆動開発ワークフロー

機能追加・仕様変更・バグ修正を、**ユーザーと合意しながら一歩ずつ**進めるためのワークフロー。

このワークフローが大事にしているのは次の2点。

- **勝手に先へ進まない。** ステアリングファイル、スコープ外の修正、リファクタリング、セキュリティ修正のどれも、ユーザーが OK を出したものだけを進める。AI が良かれと思って広げた変更は、レビューの負担と想定外の不具合を増やすだけになる。
- **作業の記録を残す。** 「何を・なぜ・どう変えたか」と「どこまで終わったか」を steering/ に残す。セッションが切れても続きから再開でき、後から経緯を追える。

以下で `SKILL_DIR` はこの SKILL.md があるディレクトリを指す。

## 他のスキルとの関係

- このスキルが動いている間は、superpowers の `brainstorming` / `systematic-debugging` / `writing-plans` / `executing-plans` / `subagent-driven-development` / `test-driven-development` などのプロセス系スキルは呼ばない。それらの手順（設計ドキュメントを別の場所に書く、一気に実装する、など）がこのワークフローとぶつかるため。ヒアリングやデバッグの観点を参考にするのは構わない。
- リファクタリング確認には `simplify`、セキュリティ確認には `security-review` を使う（手順4・6）。
- git commit はユーザーの指示があるまでしない。

---

## 全体の流れ

| # | 機能追加・仕様変更 | バグ修正 |
|---|---|---|
| 0 | 再開の判定・モード判定・規模の確認 | 同左 |
| 1 | ヒアリング（`references/feature.md`） | バグ調査（`references/bugfix.md`） |
| 2 | ステアリングファイル作成（1ファイルずつレビュー） | 同左（design.md に調査結果を書く） |
| 3 | tasklist.md に従ってテスト駆動で実装 | 同左 |
| 4–5 | リファクタリング確認 → 同意した箇所だけ修正 | 同左 |
| 6–7 | セキュリティ確認 → 同意した箇所だけ修正 | 同左 |
| 8 | ユーザーが実環境でテスト | 同左 |

手順1だけがモードで変わり、手順2以降は共通。

---

## 0. 開始時の判定

### 再開かどうか

プロジェクトルートの `steering/` 配下に、未チェック（`- [ ]`）の項目が残っている `tasklist.md` があるか確認する。

- **今回の依頼がその続きの場合**（「続き」「次のタスク」、または内容が一致する場合）は再開する。そのディレクトリの4ファイルを読み、最初の未チェック項目から続ける。ユーザーには「`steering/20260925-xxx/` の タスク 3 から再開します」のように一言伝える。
- **別件の場合**は新規として始める。未完了の steering があることは一言だけ伝える。

### モード判定

依頼内容から「機能追加・仕様変更」か「バグ修正」かを判定し、どちらとして進めるかを最初に伝える。どちらとも取れる場合は（「期待と違う動き」が仕様どおりなのかバグなのか、など）ユーザーに聞く。途中でモードが変わると分かったときも、止まって伝える。

### 規模の確認

1行の修正、typo、文言変更など明らかに小さい変更のときは、フルの手順で進めるか簡略化するかを**ユーザーに確認する**。自分の判断で省略はしない。確認するときは選択肢を示す。

- A. フル手順（4ファイル作成）
- B. 簡略版（requirements.md と tasklist.md だけ作成し、design と test_case の要点は tasklist.md に含める）
- C. ステアリングなしで修正（手順4以降のリファクタリング確認・セキュリティ確認・実環境テストは行う）

規模が普通以上なら確認は不要で、フル手順で進める。

---

## 1. ヒアリング／バグ調査

- 機能追加・仕様変更 → `references/feature.md` を読んで進める。
- バグ修正 → `references/bugfix.md` を読んで進める。

どちらも、ステアリングファイルを書き始める前に**コードベースを読んで**、既存の構成・命名・テストの書き方・使っている言語とテストフレームワークを把握する。言語やフレームワークをユーザーが指定した場合はそれに従う。既存のテストの仕組みがない場合は、何を使うかをユーザーに確認する（提案はしてよい）。

---

## 2. ステアリングファイルの作成

### 置き場所

```
steering/[YYYYMMDD]-[開発タイトル]/
```

- プロジェクトルート直下の `steering/` に作る。
- 日付は作業開始日。開発タイトルは英小文字のケバブケースで、内容が分かる短い名前にする（例: `20260925-add-tag-feature`、`20260925-fix-filter-bug`）。
- ディレクトリ名は最初のファイルを出すときにユーザーに見せる。

### 作成順とレビュー

**requirements.md → design.md → test_case.md → tasklist.md** の順に、**1ファイルずつ**作る。

1ファイル書いたら、そこで止めてユーザーにレビューを頼む。OK が出るまで次のファイルにも実装にも進まない。修正依頼があれば直して、もう一度見てもらう。後のファイルは前のファイルを前提にしているので、前が固まらないうちに進めると手戻りになる。

レビューを頼むときは、ファイルのパスと要点（3〜5行）、特に判断してほしい点（前提を置いた箇所や、選択肢がある箇所）を添える。ファイル全体をチャットに貼り直す必要はない。

test_case.md を tasklist.md より前に作るのはテスト駆動のため。先にテストケースを決め、tasklist.md の各タスクを「どのテストケースを通すか」で書けるようにする。

### 各ファイルの中身

テンプレートと書き方の注意は `references/templates.md` にある。ファイルを作る前に読む。必須項目（※）は省略しない。

- **requirements.md**：変更・追加する機能の説明（※）、受け入れ条件（※）、制約事項
- **design.md**：バグの調査結果（バグ修正のみ・※）、実装アプローチ（※・変更内容をコードで書く）、変更するコンポーネント（※）、影響範囲の分析（※）、データ構造の変更（あれば）
- **test_case.md**：単体テスト、結合テスト、必要に応じてテストケース表（表の方が分かりやすければ表を使う）
- **tasklist.md**：具体的な実装タスク（※・チェックボックス）、完了条件、動作確認チェックリスト（※・機能ごと・「どんなデータを用意し、どんな条件で、どうなるか」が分かる粒度）

---

## 3. 実装（テスト駆動）

tasklist.md の上から順に進める。各実装タスクで次のサイクルを回す。

1. test_case.md の該当ケースをテストコードにする
2. テストを実行し、**失敗すること**を確認する（失敗しないならテストが正しく書けていない可能性がある）
3. 実装する
4. テストを実行し、成功することを確認する。既存のテストも壊れていないか確認する
5. tasklist.md のそのタスクを `- [x]` に更新する

タスクが1つ終わるごとに tasklist.md を更新する。まとめて更新すると、途中で中断したときに進捗が分からなくなる。

### 想定外のことが見つかったら止まる

実装中に次のことが起きたら、**その場で手を止めてユーザーに報告する**。

- tasklist.md にない課題・バグ・必要な作業が見つかった
- 同じタスク番号の中でも、想定より対応範囲が大きいと分かった（変更ファイルが増える、設計の前提が崩れる、など）
- design.md の実装アプローチどおりでは実現できないと分かった

報告では、何が見つかったか、なぜ必要か、対応案を伝える。そのうえで tasklist.md に追記するタスク案（必要なら design.md / test_case.md の修正案も）を示し、**ユーザーの確認を得てから**追記して着手する。「ついでに直しておきました」はしない。スコープ外の変更は、レビューされないまま紛れ込むのが一番危ないため。

---

## 4–5. リファクタリング確認

実装タスクがすべて完了し、テストが通っている状態で行う。

1. `simplify` スキルを呼び、**今回の変更箇所**を対象に確認する。simplify は通常そのまま修正まで適用するので、呼ぶときに「指摘の列挙のみ行い、修正は適用しない」と指示する。それでも変更が加わった場合は、その差分をユーザーに見せて、同意のない変更は元に戻す。
2. 指摘を番号付きの一覧にしてユーザーに見せる。各項目には場所（`file:line`）、内容、直すメリットを書く。指摘がなければ「指摘なし」と伝えて次へ進む。
3. ユーザーが同意した番号だけを修正する。修正後にテストを再実行する。
4. tasklist.md のレビュー工程のチェックを更新する（対応した項目・見送った項目を一言残す）。

---

## 6–7. セキュリティ確認

1. `security-review` スキルを呼び、今回の変更に脆弱性がないか確認する。
2. 指摘を番号付きの一覧にして、深刻度（高・中・低）、場所、内容、対応案を添えてユーザーに見せる。指摘がなければ「指摘なし」と伝える。
3. ユーザーが同意した番号だけを修正し、テストを再実行する。
4. tasklist.md のレビュー工程のチェックを更新する。

---

## 8. ユーザーによる実環境テスト

tasklist.md の「動作確認チェックリスト」をユーザーに示し、実環境（ブラウザ、実機、ステージングなど）で確認してもらう。起動方法など、確認に必要な手順があれば添える。

- ユーザーから結果を聞いたら、tasklist.md の動作確認チェックリストを更新する。
- 不具合が報告されたら、手順3の「想定外のことが見つかったら止まる」と同じ扱いにする。原因を調べて報告し、tasklist.md にタスクを追記する案を出し、確認を得てから直す。
- すべて OK になったら、変更したファイルの一覧と steering ディレクトリのパスを伝えて完了とする。コミットはユーザーから指示があれば行う。
